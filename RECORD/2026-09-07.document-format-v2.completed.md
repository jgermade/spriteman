# 2026-09-07 — Document format v2: one owner for the artwork

## 1. Goal / Context

The last item left open by the performance work: the saved document carried the same
pixels up to three times — once per layer, once as the flattened composite, and once more
inside each animation clip — which was most of the remaining save cost.

While measuring it, a second and more serious problem surfaced: because `layers[]` held
one set of pixels shared by every clip, **creating a second animation and painting in it
pulled the first clip's artwork in**. Confirmed with a failing test before any change.
That made this a correctness fix, not only a size one.

Option B from the proposal was chosen: one owner for the artwork **and** a run-length
codec.

## 2. Tasks & Changes

### The format

`docs/format.md` is the new specification. In short:

- `layers[]` is the skeleton only — hierarchy, draw order, transform tracks — shared by
  every clip, and exactly the subset the Rust engine deserializes.
- `animations[].cels[layerId][frameIndex]` is the single place artwork lives.
- A cel is a palette plus run-length pairs in row-major order (`{ "p": [...], "r": [...] }`,
  index 0 = transparent). The runs always cover `canvas_width * canvas_height`, so a
  decoder needs nothing but `meta` — the spec includes a four-line decoder.
- The flattened composite is no longer stored; it is rebuilt from the cels on load.

### Code

- **`src/helpers/cel.helper.ts`** (new): `encodeCel` / `decodeCel`. Out-of-bounds pixels
  are dropped, an empty cel encodes to `null` so it can be omitted, and a damaged cel
  decodes to whatever it can rather than throwing.
- **`src/services/project.service.ts`**:
  - `AnimationClipData.cels` replaces `frame_pixels`; `syncActiveAnimation()` writes the
    working set back per layer and `adoptClipCels()` loads a clip's cels into the layers,
    which is what makes clips independent.
  - `buildJson()` writes v2; `setProjectJson()` detects the version and migrates v1
    (`isVersion2`, `readClipsV2`, `migrateClipsV1`).
  - `createNewProject()` emits v2.
  - `interpolateMotion()` now writes its in-betweens into the **owning layer** instead of
    only into the composite. They used to be lost on reload, because the composite is
    rebuilt from the layers — a pre-existing bug the format change forced into the open.
  - Cels are replaced rather than mutated in place (`setPixel`, `setPixels`, `erasePixel`,
    `erasePixels`), so an untouched cel keeps its identity and its cached encoding: a save
    re-encodes only what the user actually changed.

### Migration

v1 documents open unchanged and are rewritten as v2 on the next save. The active clip
recovers its artwork per layer; the other clips only ever had a flattened composite, so it
lands on the bottom-most layer, where a flattened image belongs. A document with no
`version` field is treated as v1 unless it contains `cels`.

## 3. Verification

```bash
npm test        # tsc --noEmit → 0 errors; vitest → 63 passed; cargo test → 13 passed
npx vite build  # 225.95 kB JS + 5.36 kB Spanish chunk; 241.57 kB wasm
```

17 new frontend tests: codec round-trips (ordinary, fully painted, empty, out-of-bounds,
damaged input, size), v2 documents (no composite, no layer pixels, round trip, layer
identity preserved), multi-animation isolation (the bug above, in both directions and
across a save), and v1 migration (per-layer recovery, flattened non-active clips, and a
document with no `animations` at all).

End-to-end in a browser, migrating a real v1 project stored the old way (in
`localStorage`, 24 frames × 3 layers, sprite-like artwork):

| | |
| --- | --- |
| Artwork after migrating | intact (75 502 painted pixels on the canvas) |
| Document size | **153 kB → 10 kB (−93.5%)** |
| Structure written | `version: 2.0.0`, no `frame_pixels`, no `layers[].frame_pixels`, 3 layers × 24 cels |
| Artwork after reloading the v2 document | identical |
| Page errors | none |

Save cost on the worst-case bench project (random noise, 24 frames × 3 layers):

| | Before | After |
| --- | --- | --- |
| `JSON.stringify` per save | 121 ms | **2–3 ms** |
| Long tasks, first save after opening | 534 ms (pre-remediation) | 185 ms (encodes every cel once) |
| Long tasks, subsequent saves | — | **none** |

Layer drag now completes with no long task at all.
