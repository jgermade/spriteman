# 2026-09-07 — GitHub Actions: build and release

## 1. Goal / Context

The repository had no CI, so nothing verified `npm test` on a pull request — the suites
only ever ran locally. Two workflows were requested: `build.yml` to test and build, and
`release.yml` to run the build, bump the version, publish a GitHub release and deploy to
GitHub Pages.

## 2. Tasks & Changes

### `.github/workflows/build.yml`

Runs on pushes to `main`, on every pull request, and as a reusable workflow
(`workflow_call`) so the release validates exactly the same way.

Steps, in the order a contributor would run them:

1. Node 22 with the npm cache; `rustup target add wasm32-unknown-unknown` (Rust itself
   ships with the runner image).
2. Cache for `~/.cargo` and `engine/target`, keyed on `engine/Cargo.toml`.
3. `wasm-pack` from the prebuilt installer, falling back to `cargo install wasm-pack
   --locked` if the download is unavailable.
4. `npm ci` → `npm run build:wasm` → `npm run typecheck` → `npm run test:web` →
   `cargo test` → `npm run build:web`.
5. Uploads `dist` as an artifact (`if-no-files-found: error`), which the release consumes.

The engine is built before the type check on purpose: `src/wasm/index.ts` imports the
generated bindings, so `tsc` fails without them. Verified by deleting `src/wasm/pkg` and
watching the type check fail with exactly that error.

Pull requests cancel superseded runs; pushes to `main` do not.

### `.github/workflows/release.yml`

Manual (`workflow_dispatch`) with a `bump` choice of `patch` / `minor` / `major`.

1. **build** — calls `build.yml`. Nothing is published unless it passes.
2. **release** — `npm version <bump> --no-git-tag-version`, then an `awk` pass that
   updates only the `[package]` version in `engine/Cargo.toml`, never a dependency's
   (checked against the real file: the `serde` and `wasm-bindgen` version fields are left
   alone). Commits, tags `v<version>`, pushes both, and publishes the release with
   `gh release create --generate-notes`, attaching the bundle as
   `spritemotion-<version>.zip`.
3. **pages** — deploys the same artifact with the first-party
   `configure-pages` / `upload-pages-artifact` / `deploy-pages` actions.

Permissions are per job: `contents: write` only for the release job, `pages: write` and
`id-token: write` only for the deployment. A `release` concurrency group keeps two
releases from overlapping. The version-bump push uses `GITHUB_TOKEN`, which does not
trigger workflows, so it cannot loop back into a build.

### `vite.config.js`

Added `base: './'`. GitHub Pages serves the site from `https://<user>.github.io/spriteman/`,
and the default absolute `/assets/…` URLs would 404 there. The relative base only applies
to builds; the dev server still serves from `/`.

## 3. Verification

The whole CI sequence was run locally, in the workflow's order:

```
npm ci                 → ok (lockfile in sync)
npm run build:wasm     → ok
npm run typecheck      → 0 errors
npm run test:web       → 63 passed
cargo test             → 3 suites ok (13 tests)
npm run build:web      → ok
```

Both workflow files parse as valid YAML, and the job graph is as intended
(`release` needs `build`; `pages` needs `build` and `release`).

The production bundle was served from a subpath to reproduce what Pages does
(`http://localhost:4180/spriteman/`) and driven in a browser:

| | |
| --- | --- |
| Editor mounts | yes |
| WebAssembly asset | `200 …/spriteman/assets/spritemotion_bg-*.wasm` |
| Engine evaluating | yes — inspector shows `Base Layer, Z: 0, 100%, TX/TY 32.0, 32.0` |
| Requests ≥ 400 | none (other than the sandbox blocking Google Fonts) |

The dev server was re-checked with the relative base: the editor mounts and the sample
project renders, with no page errors.

## 4. One-time repository setup

GitHub Pages must be switched to Actions as its source: **Settings → Pages → Build and
deployment → Source: "GitHub Actions"**. The release job also pushes the version commit
to the branch it is dispatched from, so a branch protection rule on `main` would need to
allow it.
